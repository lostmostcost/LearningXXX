# OPS-001 · 2인 병렬 개발·AI 작업 규약

Source: https://app.notion.com/p/40bbd7ec20cd81e2b1f6f6256e402133?pvs=204
Snapshot: 2026-11-02 · v0.2.2 · Notion is authoritative; refresh after approved changes.

## 기록의 역할
Notion은 제품 요구·WBS 상태·결정·사용자 QA의 원본이다. GitHub는 코드·계약·실행 가능한 테스트·PR·커밋의 원본이다. repo docs/specs는 특정 시점의 기획 스냅샷이며 원문 URL·버전을 포함한다. 자동 양방향 동기화는 현재 구현하지 않았다. 충돌 시 최신 승인 CR과 실제 병합 commit을 확인하고 조용히 덮어쓰지 않는다.

## 작업 선택과 선점
모든 WBS는 미배정으로 시작한다. Ready 중 P0→P1→P2, 순서 오름차순으로 고른다. Ready는 선행 작업의 완료/계약 병합과 미결정 해소를 확인한 상태다. 두 사람 모두 각자 구현 중 작업 하나를 기본으로 한다.
Notion 담당자 변경만으로 원자적 선점이 된다고 간주하지 않는다. Git remote의 task 및 area claim ref를 create-only 방식으로 확보한 뒤 구현 브랜치를 만들고 Notion 담당자·시작일·브랜치를 갱신한다. 충돌하면 다른 Ready 작업을 고른다. 공통 공유 파일은 shared lock이 필요하다. claim 도구가 아직 검증되지 않았거나 원격 접근이 없으면 구현을 시작하지 않고 상대와 동기적으로 확인한다.
영역 확대는 새 claim 획득→WBS 수정→관련자 확인 순서다. 활성 claim을 자동 만료시키거나 다른 사람 claim을 강제 덮어쓰지 않는다. 중단할 때는 PR/commit·다음 단계·남은 파일·테스트 결과를 기록하고 본인 claim을 해제한다. 비상 인수인계는 두 사람 확인 후 기록한다.
영역 밖 수정은 최소화한다. 선점 해제를 기다리면 작업이 막히는 등 불가피하고 담당 개발자가 승인한 예외에서만, 필요한 최소 파일에 한해 다른 area의 경로를 수정할 수 있다. 다른 사람의 claim ref는 지우거나 덮어쓰지 않는다. 수정한 파일과 이유를 해당 WBS의 paths·scope_note와 PR의 '영역 밖 수정' 항목에 기록하고 그 area의 선점자에게 알린다.
영역 밖 수정이 있는 PR은 병합 직전에 코드를 철저히 검사한다. ① 최신 main으로 갱신하고 영역 밖 diff를 한 줄씩 검토한다. ② 선점 작업이 먼저 병합됐다면 충돌을 손으로 섞지 않고 lockfile 같은 생성 파일은 컨테이너에서 다시 생성한다. ③ frozen lockfile 설치를 포함한 전체 컨테이너 검사, fresh clone 검사, check_scope를 통과한다. ④ 검사 명령과 결과를 PR에 남긴다. 하나라도 통과하지 못하면 병합하지 않는다.

## 브랜치와 PR
브랜치: feat/WBS-012-short-name, fix/WBS-012-short-name, spike/WBS-001-short-name. 하나의 작업/검토 가능한 변경 단위당 하나의 브랜치와 PR. 공유 통합 main은 직접 개발하지 않는다. 기능 미완성은 Draft PR로 조기 공유한다.
commit: type(scope): concrete change [WBS-012]. 본문에는 Why, Requirements, Validation, Limitations를 실제 내용으로 기록한다. 대규모 'update/fix' 메시지만 남기지 않는다. PR에 Notion WBS/기획 버전/REQ ID, 변경 경로, 테스트 명령과 결과, 간단한 작동 설명과 알려진 미검증을 포함한다. 주요 기능에만 본인 자가 테스트 결과를 덧붙이며 모든 PR에 QA 양식을 요구하지 않는다.
필수 상대 리뷰 승인 건수는 0건이다. 작성자는 자체 검토·CI 통과 후 자기 PR을 병합할 수 있다. 상대 코드 리뷰·상대 QA는 선택이다. 일반 작업은 적절한 확인 후 완료 처리하고, 주요 기능 완성 시에만 담당 개발자가 직접 자가 테스트한다. 개인정보·강의 원본·쿠키·인증키는 commit하지 않는다.

## 상태 전이와 완료 정의

기본 흐름은 Backlog → Ready → In Progress → Review → Done이다. Review는 작성자의 자체 확인·필요 검사·CI 단계이며 상대 승인 대기가 아니다.
일반 작업은 요구 범위를 충족하고 적절한 검사·병합·문서 갱신을 마치면 Done으로 진행한다. 별도 QA 카드·상대 실행·사람 승인 단계를 요구하지 않는다.
주요 기능 완성 시점인 WBS-020(A 핵심 흐름), WBS-028(B 녹음·전사), WBS-031(앱 수정)에서만 담당 개발자가 직접 기능을 사용해 자가 테스트하고 빌드·핵심 경로·결과를 짧게 기록한다. 자가 QA 후 본인이 완료 처리하고 다음 단계로 진행할 수 있다.
Human QA 상태는 주요 기능 자가 테스트에 필요할 때만 선택적으로 사용한다. WBS-029는 기존 결과·문제를 정리하며 별도 상대 QA나 반복 승인 절차를 추가하지 않는다. Blocked는 실제 의존성·구현 문제에 사용하며 상대 QA 대기는 차단 사유로 삼지 않는다.

## 단계별 AI 자체 코드 리뷰·수정 (필수)
CR-AI-REVIEW-2026-11-02 · 사용자 직접 지시로 승인. 현재 진행 중인 작업의 남은 단계부터 적용한다.
각 논리적 구현 단계(함수·모듈·사용자 흐름 등)는 코드 작성 → 실제 diff와 관련 코드·호출부를 검토자 관점에서 자체 리뷰 → 버그·설계 결함 수정 → 영향에 맞는 검사 → 수정 결과 재리뷰를 마친 뒤 다음 단계로 넘어간다. PR 직전 한 번의 검토로 대신하지 않는다.
검토 범위는 요구·정확성, API/데이터 계약과 소유권, 오류·취소·재시도·재시작, 동시성, 세션·계정 경계, 경로·권한·개인정보, 호환성과 복구를 포함한다. 정상 경로뿐 아니라 실패 조건과 다른 모듈의 상호작용을 확인한다. 테스트 통과만으로 코드 리뷰를 수행했다고 쓰지 않는다.
허용 범위 안의 결함은 수정하고 관련 회귀 검사 또는 위험에 맞는 확인 후 다시 리뷰한다. 정확성·보안/개인정보·데이터 손실·격리·수용 조건을 막는 미해결 결함은 해당 단계의 다음 진행 및 병합·Done을 차단한다. 새 결정·경로·claim이 필요하면 재현 근거와 차단 사유를 기록하고 권한을 해결하며, 결함을 조용히 넘기거나 임의로 범위를 넓히지 않는다. 비차단 후속 항목은 남겨도 되는 이유와 추적 위치를 기록한다.
WBS 또는 PR에 단계·검토한 파일/commit, 발견 문제의 위치·영향·원인, 수정 내용, 실제 검사 명령·결과, 재리뷰 결과·잔여 위험을 짧게 남긴다. 발견이 없으면 실제 검토 범위와 결과를 기록하고 결함을 꾸며내거나 무결함을 보증하지 않는다. 마지막 통합/PR 단계에서는 최신 main 대비 전체 diff를 검토해 단계 사이의 누락과 상호작용을 다시 확인한다.
이는 구현 AI 자신의 리뷰·수정 의무다. 별도 에이전트·상대 승인·추가 사람 QA 카드나 작은 수정마다 전체 검사 재실행을 의무화하지 않는다. 기존 claim·최종 필수 검사·주요 기능 담당 개발자 자가 테스트 규칙은 유지한다.

## AI 에이전트 입력 계약
반드시 제공: 목적, WBS ID, REQ ID, 기획 버전/URL, 허용 수정 경로, 수정 금지 경로, 의존성 commit, 수용 조건, 테스트 명령, 출력 형식.
에이전트는 Ready/claim/계약을 먼저 확인하고 요청 밖 변경을 확장하지 않는다. 모호함은 결정 필요로 기록한다. 코드 없는 계획을 구현 완료로, 테스트 미실행을 성공으로 쓰지 않는다. repo에 접근 가능한 spec snapshot만 보고 최신성을 확신하지 말고 Notion 기준 버전을 확인한다.
작업 종료 보고: 변경된 사용자 행동 → 작동 구조 → 실제 검증/미검증 → 실행 방법 → 단계별 자체 리뷰의 발견·수정·검사·재리뷰 결과 → 주요 기능이면 담당자 자가 테스트 결과 → 다음 작업. 비밀정보와 비공개 강의 내용은 공개 이슈나 로그에 넣지 않는다.

## 변경 관리와 공동 수정
두 협업자는 Notion 기획서를 직접 수정할 수 있도록 PM 페이지의 편집 공유를 사용한다. PM Share에서 팀스페이스 멤버 2명과 워크스페이스 사용자의 전체 허용 권한을 확인했다. 문장 교정은 이력만 남긴다. 범위·계약·수용 조건 변경은 CR을 만들고 기존/변경/이유/영향 REQ/WBS/데이터/테스트를 기록한다. 영향을 기록해 공유하고 기준 문서 버전을 올려 관련 작업을 재계획한다. 상대 검토·QA 승인을 의무로 두지 않는다.
공통 문서 같은 문단을 동시에 편집하지 않도록 CR에서 수정 절을 나누며, 동시에 저장된 수정은 직전 버전과 비교한다. AI는 사람의 승인/QA 결과를 대신 작성하지 않는다.
