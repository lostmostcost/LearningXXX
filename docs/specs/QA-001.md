# QA-001 · 주요 기능 개발자 자가 테스트 기준

Source: https://app.notion.com/p/40bbd7ec20cd8162abefd52e61856ced?pvs=204
Snapshot: 2026-11-01 · v0.2.0 · Notion is authoritative; refresh after approved changes.

## 적용 원칙
사용자 결정에 따라 모든 WBS에 QA나 상대방 QA를 요구하지 않는다. 주요 기능이 실제로 완성됐을 때 담당 개발자 본인이 직접 기능을 사용해 자가 테스트하고 다음 단계로 진행한다. 상대 개발자의 실행·승인·별도 QA 카드 통과를 기다리지 않는다.

## 일반 작업의 완료
문서·기획·환경·계약·작은 구현·리팩터링은 작업에 맞는 확인과 필요한 자동 검사·CI를 마치고 작성자가 병합하면 Done으로 진행할 수 있다. 이런 작업에는 별도 사람 QA 단계를 만들지 않는다. 기술 스파이크에서 실제 실행으로 입증해야 하는 항목은 증거를 남기되 같은 검증을 상대 Mac에서 다시 수행하도록 요구하지 않는다.

## 주요 기능 자가 테스트 시점
| 시점 | 담당 개발자가 직접 확인할 핵심 흐름 |
| --- | --- |
| WBS-020 · A 주요 기능 | 수집·동기화된 PDF 열기 → 첨부/캡처 채팅 → 세션 재개/독립 모드 → 번역 → 허용 폴더 작업·확인 후 휴지통 삭제 |
| WBS-028 · B 주요 기능 | 녹음/영상 원본 열기 → 자동 전사 → 전사 구간·채팅 연결과 실패 후 재시도 |
| WBS-031 · 앱 수정 | 사용자 요청 → 코드 변경·diff → 빌드·재시작 → 실패 시 정상본 복구 |
개별 하위 작업마다 위 테스트를 반복하지 않는다. 각 주요 기능을 완성한 개발자가 자기 영역의 대표 경로를 확인하며, 서로 다른 개발자가 만든 부분도 개발자 본인의 확인 기록으로 묶는다. WBS-029는 이미 수행한 자가 테스트와 알려진 문제를 정리하며 별도 상대 QA나 전 기능 재검수 단계를 추가하지 않는다.

## 최소 기록
담당 개발자가 WBS 또는 PR에 테스트한 빌드/commit, 사용한 핵심 경로, 정상 여부·수정할 문제를 짧게 남기면 된다. QA 카드·영상·스크린샷·정해진 양식·최소 사용 기간/횟수는 필수가 아니다. 작동 구조와 실행 방법은 다음 개발자가 이해할 정도로 설명한다.

## 실패와 다음 단계
주요 기능의 정상 사용을 막는 문제는 해당 개발자가 수정하고 영향 있는 경로만 다시 확인한다. 경미한 문제는 백로그에 남기고 다음 단계로 진행할 수 있다. 데이터 손실·다른 세션의 문맥 누출·핵심 기능 중단은 수정할 때까지 해당 기능을 완료로 표시하지 않는다.

## 상태와 병합
기본 흐름은 Backlog → Ready → In Progress → Review → Done이다. Review는 작성자의 확인·CI 단계이고 상대 승인을 뜻하지 않는다. Human QA 상태는 필요한 경우 주요 기능 자가 테스트 동안만 선택적으로 사용한다. 작성자는 CI 통과 후 본인 PR을 병합할 수 있다. 주요 기능은 본인 자가 테스트를 마치면 추가 승인 없이 Done과 후속 작업으로 진행한다.

## 기존 QA 카드와 이력
기존 개별 QA 카드는 참고 기록이며 미실행·미승인 상태 때문에 WBS나 병합을 막지 않는다. WBS-020/028/031에 연결된 카드만 선택적으로 자가 테스트 기록에 쓸 수 있다. 이미 기록된 증거와 과거 위임·판정은 보존하되 과거의 '상대 QA 필수' 문구는 이 정책으로 대체된다. 수행하지 않은 테스트나 사람의 행동을 수행했다고 쓰지는 않는다.


## 이전 검수 항목 참고
아래 항목은 필요한 검증을 고르는 참고 자료이며 위 최신 정책이 우선한다.

## 기능마다 사람에게 설명할 것
주요 기능 완성 시 작동 구조와 실행 방법을 간단히 설명한다. 아래 항목은 참고이며 모든 PR에 한 장의 문서를 요구하지 않는다. ①사용자가 얻는 결과 ②클릭/입력부터 결과까지의 3~6단계 흐름 ③Mac/서버/Claude 중 어디서 실행되는지 ④읽고 쓰는 파일·저장 위치 ⑤자동/수동 경계 ⑥실패 시 복구 ⑦직접 따라 할 시나리오. 내부 함수 목록만 나열하지 않는다.
예: '녹음을 중지하면 Mac에 원본이 확정되고 전사 큐에 들어갑니다. 전사 실패 시 원본은 남으며 재시도할 수 있습니다. 요약은 질문한 경우에만 생성됩니다.'

## QA 기록 계약
다음 필드는 필요할 때 쓰는 참고 항목이다: QA ID, WBS, commit/build, 환경, 검수자, 일시, 표본, 예상/실제, 증거. 주요 기능 자가 테스트도 WBS/PR에 빌드·직접 확인한 핵심 경로·결과를 짧게 기록하면 충분하며 별도 QA 카드는 필수가 아니다. 비공개 원본 첨부 대신 필요한 최소 마스킹 증거를 쓴다.
자동 테스트 결과와 사람의 사용감은 별도다. AI는 QA 준비와 실패 분석을 돕고 통과 판정/검수자/실행일을 임의 입력하지 않는다. 주요 기능이 완성되면 담당 개발자 본인이 직접 테스트한다. 상대방 QA·추가 승인은 요구하지 않는다.

## 판정과 수정
통과: 필수 수용 조건을 실제 실행하고 막히는 결함이 없다. 수정 필요: 재현 절차·기대/실제·심각도를 남기고 버그 백로그+WBS에 연결한다. 미실행: 준비 전/실행 대기 그대로 둔다. P0는 데이터 손실·계정/세션 교차·핵심 경로 불가, P1은 주요 기능 오류, P2는 우회 가능한 사용성 문제라는 초안으로 분류한다.
수정 후 동일 실패 시나리오와 영향 회귀 범위만 재검수한다. 단순 문구 수정까지 광범위한 새 테스트를 만들지 않는다.

## 게이트
G0: 구독 인증 실제 호출, 지정 fixture 파일 조작, 재개, 독립 세션 접근 검사; 실패한 필수 조건을 우회해 A로 진행하지 않는다.
G1: 새 clone→Docker 공통 검사, 두 Mac host 요구사항 확인, 공유 계약 승인, 선점 충돌 재현.
A: 수집부터 번역·채팅·세션까지 통합 시나리오, 오프라인/인증 만료/캡처 취소, 독립 세션 canary 검사, 담당 개발자의 핵심 기능 자가 테스트.
B: 녹음/온라인 다운로드 원본 재생과 자동 전사, 중단/재시도/중복 방지, 전사→채팅 연결.
전체 MVP: A+B 요구와 QA를 연결하고 미해결 결함·known limitations를 기록한다. 기간·횟수를 고정한 반복 사용 검수는 요구하지 않는다. 일반 작업은 적절한 확인·병합으로, 주요 기능은 담당 개발자의 직접 자가 테스트로 완료를 판단한다. 상대 QA나 별도 QA 카드 승인은 요구하지 않는다. 개발 목표는 착수 후 48–72시간이다.

## 미결정 지표
초기 후보는 동기화 지연, 원본 무결성, CLI 재개 성공률, 전사 표본 오류율/전문용어 정확도, 1시간 음성 처리시간, 반복 사용 빈도와 절약 시간이다. 반복 사용 빈도·기간의 최소 수치는 두지 않는다. 관측 가능한 지표는 진단에 활용하고 주요 기능 완성 시 대표 정상 경로와 필요한 실패 복구를 담당 개발자가 확인한다. 작은 하위 작업마다 사람 QA를 반복하지 않는다. 전사 품질·속도 기준은 WBS-021 엔진 실험에서 별도 결정하며 미측정 결과를 성공으로 선언하지 않는다.

## 릴리스 운영 제안
개인용 빌드도 tag/commit, 마이그레이션, 실행 방법, rollback, 데이터 위치, known issues를 남긴다. macOS 서명/배포 자동화는 외부 배포 요구가 없으므로 필요한 로컬 실행 범위부터 결정한다. 수동 테스트가 필요한 네이티브 동작을 Docker 테스트가 대신했다고 쓰지 않는다.
