## 기록의 역할
Notion은 제품 요구·WBS 상태·결정·사용자 QA의 원본이다. GitHub는 코드·계약·실행 가능한 테스트·PR·커밋의 원본이다. repo docs/specs는 특정 시점의 기획 스냅샷이며 원문 URL·버전을 포함한다. 자동 양방향 동기화는 현재 구현하지 않았다. 충돌 시 최신 승인 CR과 실제 병합 commit을 확인하고 조용히 덮어쓰지 않는다.

## 작업 선택과 선점
모든 WBS는 미배정으로 시작한다. Ready 중 P0→P1→P2, 순서 오름차순으로 고른다. Ready는 선행 작업의 완료/계약 병합과 미결정 해소를 확인한 상태다. 두 사람 모두 각자 구현 중 작업 하나를 기본으로 한다.
Notion 담당자 변경만으로 원자적 선점이 된다고 간주하지 않는다. Git remote의 task 및 area claim ref를 create-only 방식으로 확보한 뒤 구현 브랜치를 만들고 Notion 담당자·시작일·브랜치를 갱신한다. 충돌하면 다른 Ready 작업을 고른다. 공통 공유 파일은 shared lock이 필요하다. claim 도구가 아직 검증되지 않았거나 원격 접근이 없으면 구현을 시작하지 않고 상대와 동기적으로 확인한다.
영역 확대는 새 claim 획득→WBS 수정→관련자 확인 순서다. 활성 claim을 자동 만료시키거나 다른 사람 claim을 강제 덮어쓰지 않는다. 중단할 때는 PR/commit·다음 단계·남은 파일·테스트 결과를 기록하고 본인 claim을 해제한다. 비상 인수인계는 두 사람 확인 후 기록한다.

## 브랜치와 PR
브랜치: feat/WBS-012-short-name, fix/WBS-012-short-name, spike/WBS-001-short-name. 하나의 작업/검토 가능한 변경 단위당 하나의 브랜치와 PR. 공유 통합 main은 직접 개발하지 않는다. 기능 미완성은 Draft PR로 조기 공유한다.
commit: type(scope): concrete change [WBS-012]. 본문에는 Why, Requirements, Validation, Limitations를 실제 내용으로 기록한다. 대규모 'update/fix' 메시지만 남기지 않는다. PR에 Notion WBS/기획 버전/REQ ID, 변경 경로, 테스트 명령과 결과, 설명 문서, QA 시나리오, 알려진 미검증을 포함한다.
필수 상대 리뷰 승인 건수는 0건이다. 작성자는 자체 검토·CI 통과 후 자기 PR을 병합할 수 있다. 상대 코드 리뷰는 선택이며 기능 설명과 실제 사람의 사용 QA는 계속 수행한다. 병합과 WBS Done은 별개다. 개인정보·강의 원본·쿠키·인증키는 commit하지 않는다.

## 상태 전이와 완료 정의
Backlog → Ready → In Progress → Review → Human QA → Done. Blocked는 원인·해소 조건·영향 후속 작업을 기록한다.
Review: 자체 검토·CI와 적절한 영역 테스트 완료. 상대 리뷰 요청은 선택이다. Human QA: 실행 가능한 빌드/명령과 사용자 설명 전달 완료. Done: 실제 사람의 QA 판정, 필요한 수정 반영, 코드 병합, 요구/문서/증거 갱신 완료. 인프라 작업도 상대가 재현 가능한 명령을 실행해 검수한다. PR 병합만으로 Done이 되지 않는다.
QA 중 다른 작업을 시작하려면 WIP와 영역 claim을 확인한다. 기존 기능에 수정 가능성이 있으면 해당 영역을 무단 양도하지 않는다.

## AI 에이전트 입력 계약
반드시 제공: 목적, WBS ID, REQ ID, 기획 버전/URL, 허용 수정 경로, 수정 금지 경로, 의존성 commit, 수용 조건, 테스트 명령, 출력 형식.
에이전트는 Ready/claim/계약을 먼저 확인하고 요청 밖 변경을 확장하지 않는다. 모호함은 결정 필요로 기록한다. 코드 없는 계획을 구현 완료로, 테스트 미실행을 성공으로 쓰지 않는다. repo에 접근 가능한 spec snapshot만 보고 최신성을 확신하지 말고 Notion 기준 버전을 확인한다.
작업 종료 보고: 변경된 사용자 행동 → 작동 구조 → 실제 검증/미검증 → 실행 방법 → 사람에게 필요한 QA → 다음 작업. 비밀정보와 비공개 강의 내용은 공개 이슈나 로그에 넣지 않는다.

## 변경 관리와 공동 수정
두 협업자는 Notion 기획서를 직접 수정할 수 있도록 PM 페이지의 편집 공유를 사용한다. PM Share에서 팀스페이스 멤버 2명과 워크스페이스 사용자의 전체 허용 권한을 확인했다. 문장 교정은 이력만 남긴다. 범위·계약·수용 조건 변경은 CR을 만들고 기존/변경/이유/영향 REQ/WBS/데이터/테스트를 기록한다. 상대 검토 후 기준 문서 버전을 올리고 관련 작업을 재계획한다.
공통 문서 같은 문단을 동시에 편집하지 않도록 CR에서 수정 절을 나누며, 동시에 저장된 수정은 직전 버전과 비교한다. AI는 사람의 승인/QA 결과를 대신 작성하지 않는다.
