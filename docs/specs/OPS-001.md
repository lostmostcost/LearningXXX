# OPS-001 · AI 에이전트 주도 개발 규약

Snapshot: 2026-11-26 · v0.3.0 · 저장소 사본이 원본이다. 이전 2인 병렬·Notion 관리 규약(v0.2.2, https://app.notion.com/p/40bbd7ec20cd81e2b1f6f6256e402133)은 보관됐고 이력으로만 남는다.

## 기록의 역할
GitHub 저장소가 제품 요구(docs/specs), 작업 목록과 상태(docs/pm/wbs.json), 결정(docs/decisions), 검토 근거(docs/pm/reviews), 코드·테스트·PR의 유일한 원본이다. Notion PM 허브는 2026-11-26 보관됐으며 읽거나 갱신하지 않는다. 문서 안의 옛 Notion 링크는 출처 이력이다.

## 작업 선택
AI 에이전트가 개발을 주도한다. 소유자(이문찬)의 지시를 먼저 처리하고, 지시가 없으면 알려진 결함, docs/pm/backlog.md, wbs.json·리뷰 파일의 후속 항목, PRD 대비 빈 곳에서 스스로 다음 작업을 고른다. 사용자에게 보이는 실패와 데이터 손실 위험을 우선한다.
작업마다 wbs.json에 항목을 추가하고(url은 선택) 상태를 저장소에서 갱신한다. Ready 확인·CR 승인·별도 QA 카드는 필요 없다.
claim(scripts/claim.py)은 다른 사람이나 에이전트가 같은 저장소에서 동시에 작업할 때만 쓴다. 그때 다른 사람의 claim ref를 지우거나 덮어쓰지 않는다.

## 결정
구현·범위·설계 결정은 에이전트가 권장안으로 정하고 이유를 작업, 리뷰 파일 또는 docs/decisions에 남긴다. 소유자에게는 소유자 몫만 묻는다: 아직 정하지 않은 제품 방향, 개인정보·자격증명·계정 문제, 요청받지 않은 되돌리기 어렵거나 외부로 나가는 행동, AGENTS.md의 필수 요구 변경.

## 브랜치와 PR
브랜치: feat|fix|spike|docs|chore/WBS-NNN-short-name. 커밋: type(scope): concrete change [WBS-NNN]. 본문에 Why, Requirements, Validation, Limitations를 실제 내용으로 쓴다.
main은 보호 브랜치다(project-checks 필수, 일직선 기록). 브랜치를 push하고 PR을 연 뒤, 자체 검토와 CI 통과 후 에이전트가 직접 squash 머지한다. 상대 승인은 없다. main 강제 push는 금지한다. 개인정보·강의 원본·쿠키·인증키는 커밋하지 않는다(저장소는 공개).

## 완료 정의
흐름: Backlog → In Progress → Review → Done. 요구 범위 충족, 적절한 검사, 머지, 관련 문서 갱신 후 Done이다. 실제 앱이나 실제 엔진·서비스로 확인할 수 있는 변경은 에이전트가 직접 확인하고, 확인하지 못한 부분을 기록한다. 소유자의 직접 사용 테스트는 선택이며 대신 작성하지 않는다.

## 단계별 AI 자체 코드 리뷰·수정 (필수)
CR-AI-REVIEW-2026-11-02 · 사용자 직접 지시로 승인. 현재 진행 중인 작업의 남은 단계부터 적용한다.
각 논리적 구현 단계(함수·모듈·사용자 흐름 등)는 코드 작성 → 실제 diff와 관련 코드·호출부를 검토자 관점에서 자체 리뷰 → 버그·설계 결함 수정 → 영향에 맞는 검사 → 수정 결과 재리뷰를 마친 뒤 다음 단계로 넘어간다. PR 직전 한 번의 검토로 대신하지 않는다.
검토 범위는 요구·정확성, API/데이터 계약과 소유권, 오류·취소·재시도·재시작, 동시성, 세션·계정 경계, 경로·권한·개인정보, 호환성과 복구를 포함한다. 정상 경로뿐 아니라 실패 조건과 다른 모듈의 상호작용을 확인한다. 테스트 통과만으로 코드 리뷰를 수행했다고 쓰지 않는다.
결함은 수정하고 관련 회귀 검사 또는 위험에 맞는 확인 후 다시 리뷰한다. 정확성·보안/개인정보·데이터 손실·격리·수용 조건을 막는 미해결 결함은 해당 단계의 다음 진행 및 병합·Done을 차단한다. 결정이 필요하면 권장안으로 정하고 근거를 기록한다. 결함을 조용히 넘기지 않는다. 비차단 후속 항목은 남겨도 되는 이유와 추적 위치를 기록한다.
WBS 또는 PR에 단계·검토한 파일/commit, 발견 문제의 위치·영향·원인, 수정 내용, 실제 검사 명령·결과, 재리뷰 결과·잔여 위험을 짧게 남긴다. 발견이 없으면 실제 검토 범위와 결과를 기록하고 결함을 꾸며내거나 무결함을 보증하지 않는다. 마지막 통합/PR 단계에서는 최신 main 대비 전체 diff를 검토해 단계 사이의 누락과 상호작용을 다시 확인한다.
이는 구현 AI 자신의 리뷰·수정 의무다. 별도 에이전트·상대 승인·추가 사람 QA 카드나 작은 수정마다 전체 검사 재실행을 의무화하지 않는다. 최종 필수 검사는 유지한다.

## 작업 종료 보고
변경된 사용자 행동 → 작동 구조 → 실제 검증/미검증 → 실행 방법 → 단계별 자체 리뷰의 발견·수정·검사·재리뷰 결과 → 다음 작업. 비밀정보와 비공개 강의 내용은 공개 이슈나 로그에 넣지 않는다.
